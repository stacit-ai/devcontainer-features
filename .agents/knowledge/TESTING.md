# Knowledge Base — Testing Conventions

## Test Infrastructure

Tests use the `devcontainer features test` CLI command, which:
1. Builds a temporary devcontainer image with the feature applied.
2. Runs `test/<name>/test.sh` inside the resulting container.
3. Reports pass/fail.

Install the CLI: `npm install -g @devcontainers/cli`

## Test File Structure

```
test/
├── _global/                 ← cross-feature integration tests
└── <name>/                  ← per-feature tests
    ├── test.sh              ← required: default/general tests
    ├── duplicate.sh         ← optional: idempotency tests
    ├── scenarios.json       ← optional: scenario definitions
    └── <scenario>.sh        ← one script per key in scenarios.json
```

## test.sh / duplicate.sh Format

All test scripts share the same structure:

```bash
#!/bin/bash
set -e

source dev-container-features-test-lib   # lib bundled with devcontainers/cli

check "description" <command> [args...]  # each assertion
check "description" bash -c "..."        # multi-token checks via bash -c

reportResults  # always last; exits non-zero if any check failed
```

`check` records pass if the command exits 0, fail otherwise.
`reportResults` prints a summary table and exits 1 if any check failed.

**`duplicate.sh`** is run after a second install of the feature (to verify
idempotency).  It typically re-runs the same checks as `test.sh`.

## Scenario Test Format

`test/<name>/scenarios.json` is a single JSON object where each key is a
scenario name.  Each key must have a corresponding `<scenario>.sh` script in
the same directory.

```json
{
  "with_option_a": {
    "image": "mcr.microsoft.com/devcontainers/base:debian",
    "features": {
      "<name>": {
        "<option>": "<value>"
      }
    }
  },
  "with_option_b": {
    "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
    "features": {
      "<name>": {
        "<option>": "<other-value>"
      }
    }
  }
}
```

Each scenario entry requires:
- `"image"` — the base container image
- `"features"` — feature id → options map (use feature id as key, not full reference)

The corresponding script (e.g. `with_no_tools.sh`) is a standard test script
(same format as `test.sh`) that runs inside the scenario's container.

## Running Tests Locally

```bash
# Install CLI once
npm install -g @devcontainers/cli

# Run autogenerated tests for a feature against a base image
devcontainer features test --skip-scenarios -f <name> -i mcr.microsoft.com/devcontainers/base:ubuntu .

# Run scenario tests only
devcontainer features test -f <name> --skip-autogenerated --skip-duplicated .

# Run everything
devcontainer features test -f <name> .
```

## Adding a New Feature to CI

When a new feature `<name>` is added, update **both** workflow files:

**`.github/workflows/test.yaml`** and **`.github/workflows/test-multios.yaml`**

In the `changes` job's `dorny/paths-filter` step, add:

```yaml
<name>:
  - 'src/<name>/**'
  - 'test/<name>/**'
```

No other CI changes are needed; the matrix jobs consume `changes.outputs.features`
automatically.

## CI Jobs Explained

| Job | Flag | What it does |
|---|---|---|
| `test-autogenerated` | `--skip-scenarios` | Runs `test.sh` only; matrix over base images |
| `test-scenarios` | `--skip-autogenerated --skip-duplicated` | Runs each `scenarios/*.json`; no base-image matrix |
