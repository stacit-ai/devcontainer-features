# Knowledge Base — Testing Conventions

## Test Infrastructure

Tests use the `devcontainer features test` CLI command, which:
1. Builds a temporary devcontainer image with the feature applied.
2. Runs `test/<name>/test.sh` inside the resulting container.
3. Reports pass/fail.

Install the CLI: `npm install -g @devcontainers/cli`

## Test File Structure

```
test/
├── _global/                 ← cross-feature integration tests
└── <name>/                  ← per-feature tests
    ├── compatibility.txt    ← base images to test against; drives CI matrix
    ├── test.sh              ← required: default/general tests
    ├── duplicate.sh         ← optional: idempotency tests
    ├── scenarios.json       ← optional: scenario definitions
    └── <scenario>.sh        ← one script per key in scenarios.json
```

## compatibility.txt Format

`test/<name>/compatibility.txt` lists the base images the feature is tested
against.  One image per line.  Lines starting with `#` are comments.

```
# Debian-family
mcr.microsoft.com/devcontainers/base:ubuntu
mcr.microsoft.com/devcontainers/base:debian
debian:latest
ubuntu:latest

# RPM-family
fedora:latest
almalinux:latest

# Alpine
mcr.microsoft.com/devcontainers/base:alpine
```

The CI `build-matrix` job reads this file to create the `baseImage` matrix for
`test-autogenerated`.  If the file is absent, CI falls back to
`mcr.microsoft.com/devcontainers/base:ubuntu`.

## test.sh / duplicate.sh Format

All feature test scripts use the devcontainer feature test library. Keep them
as declarative `check` lists rather than custom Bash test frameworks:

```bash
#!/bin/bash
set -e

source dev-container-features-test-lib

check "description" <command> [args...]
check "description" bash -c "..."

reportResults
```

`check` records pass if the command exits 0, fail otherwise.
`reportResults` prints a summary table and exits 1 if any check failed.
Do not define custom `assert_*` functions, loops that print their own PASS/FAIL
messages, or ad hoc summary handling in feature tests. For compound conditions,
use `check "description" bash -c "..."` so the standard library still owns
result collection and reporting.

**`duplicate.sh`** is run after a second install of the feature (to verify
idempotency).  It typically re-runs the same checks as `test.sh`.

## Scenario Test Format

`test/<name>/scenarios.json` is a single JSON object where each key is a
scenario name.  Each key must have a corresponding `<scenario>.sh` script in
the same directory.

```json
{
  "with_option_a": {
    "image": "mcr.microsoft.com/devcontainers/base:debian",
    "features": {
      "<name>": {
        "<option>": "<value>"
      }
    }
  },
  "with_option_b": {
    "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
    "features": {
      "<name>": {
        "<option>": "<other-value>"
      }
    }
  }
}
```

Each scenario entry requires:
- `"image"` — the base container image
- `"features"` — feature id → options map (use feature id as key, not full reference)

The corresponding script (e.g. `with_no_tools.sh`) is a standard test-library
script with `check` assertions and `reportResults`, same as `test.sh`.

## Running Tests Locally

Use the `just` command runner (install: `pipx install rust-just`):

```bash
# One-time setup
just setup                              # npm install -g @devcontainers/cli

# Run all tests (autogenerated + scenarios) for a feature
just test <name>

# Run autogenerated tests against every image in compatibility.txt
just test-compat <name>

# Run against a single specific image
just test-image <name> mcr.microsoft.com/devcontainers/base:ubuntu

# Run scenario tests only
just test-scenarios <name>

# Run global integration tests
just test-global
```

Equivalent bare `devcontainer` commands (if `just` is unavailable):

```bash
# Autogenerated tests only, single image
devcontainer features test --project-folder . --skip-scenarios --skip-duplicated -f <name> -i <image>

# Scenario tests only
devcontainer features test --project-folder . -f <name> --skip-autogenerated --skip-duplicated

# Everything
devcontainer features test --project-folder . -f <name>
```

## Adding a New Feature to CI

No manual CI changes are needed.  The `changes` job in both `test.yaml` and
`test-multios.yaml` automatically scans `src/` subdirectories at runtime to
generate the `dorny/paths-filter` filters.  Adding `src/<name>/` is sufficient
for the feature to be detected.

The `baseImage` matrix is built from `test/<name>/compatibility.txt`.  Create
this file when adding the feature (see format above); if omitted, CI tests only
against `mcr.microsoft.com/devcontainers/base:ubuntu`.

Both test workflows write a GitHub Step Summary listing the detected features
selected for testing.  `test-multios.yaml` also reports the generated
feature/base-image matrix.

Longer workflow `run: |` shell blocks follow the same function-oriented Bash
structure required by `.agents/knowledge/QUALITY.md`.

## CI Jobs Explained

| Job | Flag | What it does |
|---|---|---|
| `test-autogenerated` | `--skip-scenarios` | Runs `test.sh` only; matrix over base images |
| `test-scenarios` | `--skip-autogenerated --skip-duplicated` | Runs each `scenarios/*.json`; no base-image matrix |
