# Feature Add

Every feature in this repo requires three parts created together:
`src/<name>/`, `spec/<name>.md`, and `test/<name>/`.  Missing any part breaks
CI and violates the project's 1-to-1 correspondence invariant.

## Workflow

1. **Determine the feature id** — lowercase, hyphen-separated, matches the
   directory name.  The id must equal `devcontainer-feature.json`'s `"id"` field.

2. **Create `src/<name>/devcontainer-feature.json`** — use an existing feature
   under `src/` as structural reference.  Required fields: `name`, `id`,
   `version` (start at `1.0.0`), `description`.  Set `documentationURL` to
   `https://github.com/stacit-ai/devcontainer-features/tree/main/src/<name>`.

3. **Create `src/<name>/install.sh`** — must start with `#!/bin/bash` and
   `set -euo pipefail`.  Use an existing feature's `install.sh` as a boilerplate
   reference for helpers: `remote_user_do()`, `require_command()`,
   `set_remote_ownership()`.  The script always runs as root; user-side effects
   go through `remote_user_do`.

   Additional files may be placed in `src/<name>/` (e.g. helper scripts,
   config templates).  All files in this directory are included in the OCI
   artifact; files outside it are invisible to the feature at runtime.  Two
   special cases:
   - **`NOTE.md`** — optional; displayed to users as install-time hints.
   - **`README.md`** — auto-generated by `release.yaml`; never create or edit
     manually, it will be overwritten on the next release.

4. **Create `spec/<name>.md`** — document: (a) feature goals, (b) supported
   platforms and any known gaps, (c) implementation gotchas, (d) external
   reference links specific to this feature.  No fixed template; see an existing
   `spec/<name>.md` for structural guidance.

5. **Create `test/<name>/test.sh`** — use `dev-container-features-test-lib`
   format (see `.agents/knowledge/TESTING.md` for exact syntax).  Cover: binary
   on PATH, key environment variables, default option behavior.

   Optional test files (add as needed):
   - **`test/<name>/duplicate.sh`** — idempotency checks; run after a second
     install; can mirror `test.sh` assertions.
   - **`test/<name>/scenarios.json`** — a JSON object where each key is a
     scenario name; every key must have a matching `<scenario>.sh` script in
     the same directory.

6. **Add path filters to both CI workflows** — in
   `.github/workflows/test.yaml` and `.github/workflows/test-multios.yaml`,
   add a `<name>:` entry under the `dorny/paths-filter` filters block:
   ```yaml
   <name>:
     - 'src/<name>/**'
     - 'test/<name>/**'
   ```

7. **Make `install.sh` executable** — run `chmod +x src/<name>/install.sh`.

## Gotchas

- **id = directory name** — `devcontainer-feature.json`'s `"id"` field must
  exactly match the subdirectory name under `src/`.  The `validate.yml`
  workflow enforces this; mismatches cause CI failure.
- **install.sh runs as root** — never assume a user home directory without
  using `find_user_home()`.  Direct writes to `~/` that bypass `remote_user_do`
  will land in `/root/` and be invisible to the container user.
- **Both test workflows need the path filter** — `test.yaml` and
  `test-multios.yaml` each have their own independent `dorny/paths-filter`
  block.  Adding only one will silently skip multi-OS tests.
- **Increment version before release** — `release.yaml` skips already-published
  versions.  A new feature must start at `1.0.0`.
