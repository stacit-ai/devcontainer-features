# Feature Add

Every feature in this repo requires three parts created together:
`src/<name>/`, `spec/<name>.md`, and `test/<name>/`.  Missing any part breaks
CI and violates the project's 1-to-1 correspondence invariant.

## Workflow

Development follows a **spec-first, vertical-slice TDD** approach.
Write one test, implement that test, repeat — never batch tests then
batch implementation.

---

### Phase 1 — Define (no behavioral code yet)

1. **Determine the feature id** — lowercase, hyphen-separated, matches the
   directory name.  The id must equal `devcontainer-feature.json`'s `"id"` field.

2. **Create `spec/<name>.md`** — this is the source of truth and TDD backlog.
   Document: (a) feature goals, (b) supported platforms and known gaps,
   (c) the options the feature will expose, (d) implementation gotchas,
   (e) external reference links specific to this feature.

   **At the end of the spec, list user-visible behaviors in the order you plan
   to implement them.**  This ordered list becomes the TDD backlog for Phase 2.
   Example ordering:
   - binary is on PATH after install
   - correct version is selected (if `version` option exists)
   - required environment variables are exported
   - shell completion is registered (if applicable)
   - each additional option produces the expected effect
   - re-install is idempotent (`duplicate.sh`)

3. **Create `src/<name>/devcontainer-feature.json`** — use an existing feature
   under `src/` as structural reference.  Required fields: `name`, `id`,
   `version` (start at `1.0.0`), `description`.  Set `documentationURL` to
   `https://github.com/stacit-ai/devcontainer-features/tree/main/src/<name>`.
   Declare all options from the spec here; no implementation logic yet.

4. **Create stub `src/<name>/install.sh`** — two lines only:
   ```bash
   #!/bin/bash
   set -euo pipefail
   ```
   Run `chmod +x src/<name>/install.sh`.  Behavioral code is added slice by
   slice in Phase 2.  For available helper functions and common patterns, see
   `.agents/knowledge/SNIPPETS.md`.

   Additional files may be placed in `src/<name>/` (e.g. helper scripts,
   config templates).  All files in this directory are included in the OCI
   artifact; files outside it are invisible to the feature at runtime.
   - **`NOTE.md`** — optional; displayed to users as install-time hints.
   - **`README.md`** — auto-generated by `release.yaml`; never create manually.

5. **Create stub `test/<name>/test.sh`** — three lines only:
   ```bash
   #!/bin/bash
   set -e
   source dev-container-features-test-lib
   reportResults
   ```
   `check` assertions are added one at a time during Phase 2.

6. **Create `test/<name>/compatibility.txt`** — list the base images this
   feature should be tested against, one per line.  Lines starting with `#`
   are comments.  The CI `build-matrix` job reads this to build the
   `baseImage` matrix; if absent, CI falls back to
   `mcr.microsoft.com/devcontainers/base:ubuntu`.  Start with the images you
   know the feature supports and expand as you implement more OS slices.

   Example:
   ```
   mcr.microsoft.com/devcontainers/base:ubuntu
   mcr.microsoft.com/devcontainers/base:debian
   ```

7. **No manual CI filter changes needed** — both `test.yaml` and
   `test-multios.yaml` automatically scan `src/` subdirectories at runtime.
   Creating `src/<name>/` is sufficient for the feature to be detected by CI.

---

### Phase 2 — TDD Cycles (one behavior at a time)

Work through the spec's behavior backlog one item at a time.
Each cycle: **RED → GREEN → next slice**.

> **Anti-pattern — horizontal slices (do not do this)**
> ```
> WRONG:  RED:   test1, test2, test3, test4, test5
>         GREEN: impl1, impl2, impl3, impl4, impl5
>
> RIGHT:  RED→GREEN: test1 → impl1
>         RED→GREEN: test2 → impl2
>         RED→GREEN: test3 → impl3  (each cycle uses knowledge from the last)
> ```
> Batching tests first produces tests of imagined behavior, not actual behavior.
> You end up testing shape (data structures, function signatures) rather than
> user-facing outcomes.  Tests become insensitive to real breakage.

**For each behavior in the spec backlog:**

**RED — write ONE check:**
Add a single `check "description" <command>` line to `test/<name>/test.sh`
(or a new scenario script if the behavior requires a non-default option).
Run the test and confirm it **fails**:
```bash
just test-image <name> mcr.microsoft.com/devcontainers/base:ubuntu
# or without just:
devcontainer features test --skip-scenarios -f <name> \
  -i mcr.microsoft.com/devcontainers/base:ubuntu .
```

**GREEN — implement only what that check needs:**
Add to `src/<name>/install.sh` only the code required to pass the failing
check.  See `.agents/knowledge/SNIPPETS.md` for helper functions
(`remote_user_do`, `require_command`, `set_remote_ownership`, etc.).
The script always runs as root; user-side effects go through `remote_user_do`.
Run the test again and confirm it **passes**.

**Repeat** for the next behavior in the backlog.  Because you just wrote the
implementation, you know exactly which behavior matters and how to verify it.

**Scenario tests** — only create `test/<name>/scenarios.json` and the
companion `<scenario>.sh` when you reach a behavior that requires a
non-default option.  Do not pre-create scenario files for options you have not
implemented yet.

**Idempotency (`duplicate.sh`)** — add this as the final slice after all other
behaviors pass.  It typically mirrors `test.sh` assertions and is run after a
second install.

## Gotchas

- **id = directory name** — `devcontainer-feature.json`'s `"id"` field must
  exactly match the subdirectory name under `src/`.  The `validate.yml`
  workflow enforces this; mismatches cause CI failure.
- **install.sh runs as root** — never assume a user home directory without
  using `find_user_home()`.  Direct writes to `~/` that bypass `remote_user_do`
  will land in `/root/` and be invisible to the container user.  See
  `.agents/knowledge/SNIPPETS.md` for the `remote_user_do` pattern.
- **CI filters are auto-generated** — `test.yaml` and `test-multios.yaml`
  scan `src/` at runtime.  No manual edits to workflow files are needed when
  adding a feature.
- **Increment version before release** — `release.yaml` skips already-published
  versions.  A new feature must start at `1.0.0`.
- **Confirm RED before implementing** — if a check passes immediately (before
  any implementation), the check is testing the wrong thing.  Revise the check
  until it fails, then implement.
- **Use `--skip-scenarios` during early slices** — building the full scenario
  matrix for every cycle is slow.  Run scenario tests only when implementing
  the option they cover.
- **test.sh grows one check at a time** — never pre-populate `test.sh` with
  all the behaviors from the spec.  Each check is written immediately before
  its implementation.
